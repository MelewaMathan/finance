## System / Approach

The repository is an **NPM workspaces monorepo** managed through a single root `package.json` that declares three workspace packages (`backend`, `frontend`, `contracts`). Each subproject has its own `package.json` declaring runtime and dev dependencies, while the root holds shared tooling (`concurrently`, `embedded-postgres`) and cross-workspace orchestration scripts. A top-level `package-lock.json` (generated by npm) pins every transitive dependency for reproducible installs.

There is no vendoring of third-party code — all packages are resolved from the public npm registry at install time. No `.npmrc`, private registry configuration, or `GOPRIVATE`-style settings are present in the tree.

## Key Files

- `package.json` (root): declares `workspaces: ["backend", "frontend", "contracts"]`, root-level scripts that delegate to `npm --workspace <pkg> run ...`, and the `engines.node >=20` constraint.
- `package-lock.json` (root): lockfile pinning the entire dependency graph across all workspaces.
- `backend/package.json`: Express API dependencies (`express ^5.1.0`, `pg ^8.13.1`, `jsonwebtoken ^9.0.2`, `bcryptjs ^3.0.2`, `ethers ^6.17.0`, `zod ^4.0.0`, etc.) plus TypeScript/Vitest/Supertest dev deps.
- `frontend/package.json`: React 19 + Vite 8 + Tailwind 3 + TypeScript stack.
- `contracts/package.json`: Hardhat 2.22.x ecosystem (`@nomicfoundation/hardhat-toolbox ^5.0.0`).
- `docker-compose.yml`: not a package manager config, but defines the PostgreSQL service consumed by the backend.

## Architecture and Conventions

1. **Workspace layout**: The monorepo uses flat NPM workspaces. Root scripts call into workspace packages via `npm --workspace <name> run <script>` rather than using `npm -w`. This means each workspace's `package.json` owns its dependency graph independently; there is no shared `dependencies` block lifted to the root.

2. **Version ranges**: All third-party versions use caret (`^`) ranges, allowing minor/patch upgrades within the major version. Examples: `express ^5.1.0`, `react ^19.0.0`, `hardhat ^2.22.17`, `vitest ^5.0.0`. There is no exact pinning in `package.json`; actual resolution is pinned by `package-lock.json`.

3. **TypeScript across workspaces**: Both `backend` and `frontend` declare their own `typescript ^5.7.2` and `@types/*` packages locally rather than sharing them from the root, so each workspace resolves its own TS types.

4. **Node engine constraint**: The root `engines.node >=20` enforces a minimum Node.js version for anyone running the repo.

5. **No private registry / no vendoring**: No `.npmrc`, no `registry` overrides, no `vendor/` directories, no `pnpm-lock.yaml` or `yarn.lock`. Dependencies are pulled from the default npm registry.

6. **Lockfile-only determinism**: Reproducibility relies on the root `package-lock.json`. There is no explicit CI step shown here that runs `npm ci`, but the presence of the lockfile signals the intended deterministic install path.

## Conventions and Constraints

- **Observed convention**: Every workspace package is marked `"private": true`, indicating these packages are not published to npm — they are internal to the monorepo.
- **Observed convention**: Runtime dependencies live under `dependencies`; build/test/type-check tooling lives under `devDependencies` in each workspace's `package.json`.
- **Enforced constraint**: The root `engines.node` field requires Node.js `>=20` (enforced by npm when `engine-strict` is enabled or by tools reading the field).
- **Enforced constraint**: The workspace membership is declared centrally in the root `package.json` `workspaces` array; adding a new subproject requires updating this list for `npm` to discover it.
- **Enforced constraint**: Cross-workspace scripts in the root `scripts` section invoke subprojects exclusively via `npm --workspace <name> run ...`; there are no direct relative `node` invocations to workspace binaries in the root scripts.
